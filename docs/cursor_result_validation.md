# Cursor validation for Terrabot automated tests

## Purpose

Cursor is now an independent semantic verifier for completed Terrabot automated test runs.
It does not replace Terrabot's deterministic validation. The existing backend validators
remain the mandatory pre-push gate for Terraform changes.

One Cursor Cloud Agent is created after all cases in a run finish. The agent receives a
bounded evidence package for every case and returns one strict JSON verdict per case.
The final Teams report contains both the backend result and Cursor's independent result.

## Final workflow

```text
Teams: run tests
  -> Terrabot derives targets from the live Terraform repositories
  -> prompts are generated by the existing test workflow
  -> Terrabot/Foundry generates Terraform
  -> existing deterministic validators approve or reject the output
  -> approved Phase 1 output is pushed to an isolated test branch
  -> repository context is written or verified
  -> Phase 2 performs a fresh search and checks context attachment/reuse
  -> one read-only Cursor review validates all completed cases
  -> final backend + Cursor result tables are posted to Teams
```

## What Cursor validates

For every case Cursor returns:

- `output_correct`: the generated Terraform or test-branch diff implements the requested
  change in the correct repository, environment, path, and control/resource pattern.
- `context_added`: the Phase 1 repository-context record maps the user concept to the
  expected Terraform path/control and contains repository evidence.
- `context_retrievable`: the Phase 2 search returned the same exact or semantically
  equivalent repository-context mapping.
- `context_reused`: the retrieved context was attached to Foundry and allowed Phase 2 to
  resolve the correct target without another clarification.
- `overall_ok`: every applicable Cursor assertion passed.

Context fields are `null` for resource-creation cases because those cases do not run the
Phase 2 context-reuse test.

## Validation boundary

The backend performs the physical checks against GitHub and the Azure AI Search repository
index. Cursor independently evaluates the exact generated-file excerpts, hashes, branch
metadata, stored context record, Phase 2 search record, attached context IDs, and target
reuse result produced by those operations.

Cursor does not write repository context and does not receive Azure AI Search write
credentials. This preserves the existing context storage and retrieval path while adding a
second semantic review.

## Teams result

The existing detailed test table now includes:

- Cursor output
- Cursor context: `ADD`, `GET`, and `USE`
- Cursor overall result
- final classification and score

A second compact table shows:

| Test | Output correct | Context added | Context retrievable | Context reused | Overall | Reason |
|---|---|---|---|---|---|---|
| aws-01 | PASS | PASS | PASS | PASS | PASS | Independent verification completed. |

When Cursor validation is enabled, its assertions are part of the final score and full-pass
status. The original backend score is retained separately as `backend_score`. Adaptive test
coverage is persisted only after the Cursor verdict has been applied, so future case selection
uses the final score and final failure classification rather than the backend-only result.

## Function App settings

Required:

```text
TERRABOT_TEST_CURSOR_RESULT_VALIDATION_ENABLED=true
TERRABOT_CURSOR_API_KEY=<Cursor user or service-account API key>
TERRABOT_CURSOR_API_BASE_URL=https://api.cursor.com
```

Optional:

```text
TERRABOT_TEST_CURSOR_VALIDATION_MODEL=<Cursor model ID>
TERRABOT_TEST_CURSOR_VALIDATION_TIMEOUT_SECONDS=600
TERRABOT_TEST_CURSOR_VALIDATION_REQUEST_TIMEOUT_SECONDS=45
TERRABOT_TEST_CURSOR_VALIDATION_POLL_SECONDS=5
TERRABOT_TEST_CURSOR_VALIDATION_MAX_PROMPT_CHARS=180000
TERRABOT_TEST_CURSOR_VALIDATION_MAX_FILES_PER_PHASE=5
TERRABOT_TEST_CURSOR_VALIDATION_FILE_EXCERPT_CHARS=9000
```

Store the Cursor API key in Azure Key Vault and use a Key Vault reference in Function App
configuration. Do not commit the key.

## Cursor API safety settings

The Cloud Agent request uses:

```json
{
  "mode": "plan",
  "workOnCurrentBranch": false,
  "autoCreatePR": false,
  "repos": [
    {
      "url": "https://github.com/venasolutions/tf-devops",
      "startingRef": "<exact commit SHA>"
    }
  ]
}
```

The prompt explicitly prohibits edits, commits, pushes, branches, and pull requests. Terrabot
also rejects the complete Cursor verdict if the terminal run reports any entry in
`git.branches`.

Cloud Agent plan mode and branch-result checks are safeguards, not a cryptographic read-only
permission boundary. Use a dedicated Cursor service account and the narrowest repository
permissions supported by the connected source-control setup.

Search by the Terrabot run ID. Cursor-specific events use:

```text
[TerrabotCursorValidation] event=cursor_validation_started
[TerrabotCursorValidation] event=cursor_validation_agent_created
[TerrabotCursorValidation] event=cursor_validation_run_status
[TerrabotCursorValidation] event=cursor_validation_case_verdict
[TerrabotCursorValidation] event=cursor_validation_completed
[TerrabotCursorValidation] event=cursor_validation_failed
[TerrabotCursorValidation] event=cursor_validation_read_only_violation

```

No API key or complete repository file is written to logs.

## Deployment

1. Deploy the changed Python files with the existing Function App release process.
2. Add the required Function App settings. Use
   `deployment/cursor-result-validation.app-settings.example.json` as the template.
3. Confirm the Cursor account can access `venasolutions/tf-devops` and
   `venasolutions/tf-azure-hub`.
4. Restart the Function App after changing settings.
5. Send `run tests all 2` in an authorized Teams conversation for a small verification run.
6. Confirm the Teams response contains the Cursor table and the logstream contains
   `cursor_validation_completed`.
7. Run the normal `run tests` command.

Apply settings with Azure CLI after replacing the placeholders:

```bash
cp deployment/cursor-result-validation.app-settings.example.json \
  deployment/cursor-result-validation.app-settings.json

az functionapp config appsettings set \
  --resource-group <resource-group> \
  --name <function-app-name> \
  --settings @deployment/cursor-result-validation.app-settings.json
```

## Failure and rollback behavior

A Cursor API failure does not discard the completed backend run. The Teams table shows
`ERROR`, the case classification becomes `CURSOR_VALIDATION_UNAVAILABLE`, and the backend
score remains available. This makes validation failure explicit without losing the
underlying Terrabot evidence.

Disable only the Cursor review with:

```text
TERRABOT_TEST_CURSOR_RESULT_VALIDATION_ENABLED=false
```

The existing backend test, validation, branch, context, and Teams workflows then operate as
before.
